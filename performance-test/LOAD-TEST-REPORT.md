# 드롭 부하 테스트 보고서

> 측정: 2026-08-24 ~ 2026-08-26 · 대상: k3s 클러스터(EC2 2노드) · 브랜치 `feature/k3s-infra-tuning`
> 하네스: `performance-test/loadtest/`

체크리스트의 **"부하 발생 시 HPA에 의한 Pod 자동 확장 검증"**에 대한 답이다.
요구사항이라 붙이는 것이 아니라, **HPA가 이 도메인에 맞는 도구인지를 숫자로 판단**했다.

---

## 1. 요약

| 질문 | 답 |
| --- | --- |
| 300 동시 선점에서 재고 정합성이 깨지는가 | **아니오.** 오버셀 0, 성공 300/300 (전 실행) |
| HPA가 드롭 오픈 버스트에 맞는가 | **아니오.** 확장 결정 11초 + Pod Ready 69초 = 80초. 버스트는 6초에 끝난다 |
| `minReplicas: 2`로 미리 확보하면 나아지는가 | **근거 없음.** 처리량이 개선되지 않았다 |
| 요청 하나가 CPU를 얼마나 쓰는가 | **9.6ms** (JIT 예열 후, cgroup 실측) |
| 지연은 어디서 생겼는가 | **Traefik+TLS 42% / 게이트웨이 필터 21% / backend 5%** |
| 무엇을 고쳤고 얼마나 나아졌나 | 인증서 ECDSA + 게이트웨이 request 3배 → **lock p95 3.26s → 0.886s (NFR 통과)** |
| 애플리케이션 코드의 가장 큰 병목은 | **`@Transactional` 안의 Redis 왕복** — 커넥션 점유가 유휴 17ms → 부하 135ms |
| 배포는 왜 실패했나 | 2코어 노드에서 JVM 5개 동시 기동. **순차 롤아웃으로 해결** (§9-1) |

**결론 둘.**

1. **드롭은 시작 시각이 정해진 이벤트다. 반응형 오토스케일링은 구조적으로 늦다.**
   HPA는 예측하지 못한 지속 부하의 안전장치로만 두고, 드롭 오픈 대비 수단으로 쓰지 않는다.
2. **backend 를 늘리는 것은 지금 효과가 없다.** 지연의 5%만 backend 에서 생긴다.
   같은 노력이라면 **진입점**을 먼저 봐야 한다. 실제로 진입점 두 곳(TLS 인증서 종류,
   게이트웨이 CPU request)만 고쳐 **연결 재사용 경로가 NFR을 통과했다**(§8).
   애플리케이션 코드는 한 줄도 바꾸지 않았다.

## 2. 이 보고서의 숫자를 인용하기 전에

측정 환경은 **2 vCPU 노드 2대**다. node-a 한 대에 backend·api-gateway·Traefik·
core-postgres·redis·kafka·elasticsearch·ai-service가 모두 있고, 부하 생성기(k6)까지
같은 노드에서 돌렸다. **그래서 부하 구간의 병목이 애플리케이션이 아니라 측정 장비 쪽에 생긴다.**

### 답할 수 있는 것

- 재고 정합성 (오버셀·중복 선점 여부)
- **요청당 CPU** — 인스턴스 크기와 무관한 값이라 용량 산정의 기초가 된다
- HPA의 반응 시간과 Pod 배치
- 코드·설계 수준의 병목 위치
- 2배 이상 차이 나는 구성 변경의 효과

### 답할 수 없는 것

| 질문 | 왜 |
| --- | --- |
| **NFR(p95 1.5s) 충족 여부** | 지연의 대부분이 애플리케이션 밖(Traefik TLS·연결 수립)에서 생긴다(§7) |
| **몇 명까지 견디는가** | 부하 생성기가 먼저 한계에 닿는다. backend는 Tomcat 200개 중 4~61개만 썼다 |
| p95·처리량의 절대값 | 위와 같음 |
| 20% 미만의 구성 차이 | 재현 오차 6%, 표본 300(p99는 뒤에서 3번째 값) |

> **가장 흔한 오독**: "p95가 3.5초니 서비스가 느리다."
> 그 3.5초 중 **backend 서블릿 처리는 0.14초(5%)**다.
> 어디서 생기는 지연인지는 §7에 구간별로 갈라 두었다.

## 3. 무엇을 어떻게 쟀나

### 시나리오

드롭 오픈 순간을 재현한다. 계정 300개가 **동시에 1회씩** 요청한다.

| 순서 | 시나리오 | 엔드포인트 | 기대 |
| ---: | --- | --- | --- |
| 1 | confirm-entry | `POST /api/v1/drops/{id}/confirm-entry` | 300/300 성공 |
| 2 | lock-start | `POST /api/v1/drops/{id}/lock-start` | 재고 300 → 300 선점, 오버셀 0 |

`lock-start`는 `entryStatus='ENTERED'`를 요구하므로 confirm이 반드시 선행한다.
건너뛰면 전원이 DR014로 떨어져 **재고를 건드리지도 못한 채 통과한다.**

### 측정 프로토콜 — 쓰기 경로까지 예열한다

**이번 작업에서 가장 큰 소득이다.** 기존 하네스(`_common.sh`)의 예열은
`GET /drops/{id}/info` 300회뿐이라, 정작 재려는 `confirm-entry`·`lock-start`는
한 번도 실행되지 않은 채 k6가 시작한다. **측정 구간이 그대로 JIT 컴파일 구간이 된다.**

같은 구성인데 예열 유무로 이만큼 갈렸다.

| | 예열 안 됨 | 쓰기 경로까지 예열 |
| --- | ---: | ---: |
| lock p95 | 6.08s | **3.48s** |
| lock 처리량 | 44.8/s | **73.5/s** |

`TodayDropCache`가 당일 드롭을 리스트로 들고 기동 시 `refresh()` 하는 점을 이용해,
**드롭 두 개를 먼저 만들고 롤아웃을 한 번만** 한다. 첫 드롭으로 쓰기 경로를 데우고,
재기동 없이 두 번째 드롭에서 잰다.

```
계정·토큰 → 드롭 A·B 생성 → 롤아웃 1회 → 대기(60s) + 조회 예열(300회)
  → A 에 confirm+lock (버림)
  → B 에 confirm+lock (측정)
```

예열이 끝났는지는 **요청당 CPU가 평평해졌는지**로 판단한다.

```
예열 GET 300회   15.4ms
버리는 confirm   14.2ms
버리는 lock      10.1ms
측정 confirm      9.6ms   <- 평평
측정 lock        10.2ms
```

### 계측 — 게이지가 아니라 누적 카운터

`process.cpu.usage`는 JVM이 자체 계산하는 롤링값이라 1초 해상도로 처리량과 짝지으면
오차가 크다. 실제로 이 값으로 "CPU가 병목"이라는 **오진을 한 번 냈다**(같은 CSV의
다른 행은 0.0이었다). 그래서 요청당 CPU와 커넥션 대기/점유는 **누적 카운터의 구간 차이**로 계산한다.

```
요청당 CPU   = cgroup cpu.stat usage_usec 차이 / 요청 수 차이
acquire 평균 = hikaricp_connections_acquire_seconds_sum 차이 / count 차이
usage 평균   = hikaricp_connections_usage_seconds_sum   차이 / count 차이
```

### 도구

| 파일 | 역할 |
| --- | --- |
| `loadtest/warm-measure.sh` | 쓰기 경로까지 예열하는 측정. `PREP_ONLY=true`면 준비까지만 |
| `loadtest/poll-backend.py` | 누적 카운터 1초 수집 (cgroup + `/actuator/prometheus`) |
| `loadtest/poll-report.py` | 부하 구간 자동 탐지 + 구간 차이로 지표 계산 |
| `loadtest/run-k6-local.sh` | k6만 다른 호스트에서 실행 |
| `loadtest/poll-gateway.py` | 게이트웨이 누적 카운터. 총처리 − 업스트림 = 필터 체인 몫 |
| `drop-lock-warm-connection.js` | 연결을 미리 세우고 재는 lock 변형 |

두 폴러 모두 **cgroup PSI(`cpu.pressure`)** 를 함께 수집한다. `cpu.stat`의
`throttled_usec`은 "자기 쿼터 초과"만 세기 때문에, 노드 경쟁에서 밀려 스케줄을
받지 못한 시간은 PSI로만 보인다. 게이트웨이 진단이 이 지표로 갈렸다(§8-2).

## 5. 결과 — HPA

### 5-1. 확장 타이밍 (min=1, max=2)

```
08:11:02   부하 시작
08:11:13   두 번째 Pod 생성      <- 확장 결정까지 11초
08:12:22   두 번째 Pod Ready     <- 생성 후 69초 / 부하 시작 후 80초
```

**부하는 6초에 끝났다. 두 번째 Pod는 한 요청도 처리하지 못했다.**
8/24 측정에서도 확장 결정은 11초로 같았다(그때는 Ready에 도달하기 전에 부하가 끝났다).

시간이 어디로 가는지는 구조적이다.

```
감지     11초     (실측. metrics-server 15s + HPA 평가 15s 주기라 최대 30초까지 늦을 수 있다)
JVM 기동 69초     (실측. startupProbe 유예는 240초, 노드가 붐비면 200초까지 걸린 적도 있다)
────────────────
확장 완료까지 80초 (실측) ~ 최대 4분
```

**둘 다 줄일 수 있는 성질이 아니다.** 감지는 metrics-server의 수집 주기가 하한이고,
기동은 JVM 시작 시간이다. 인스턴스를 키워도 수십 초 단위는 그대로 남는다.

**드롭 오픈의 부하 피크는 30초 안에 끝난다. HPA는 구조적으로 늦다.**

### 5-2. `minReplicas: 2` — 사전 확보 효과 없음

| 지표 | replica 1 | replica 2 |
| --- | ---: | ---: |
| confirm p95 | 3.63s | 7.47s |
| confirm 처리량 | 70.6/s | 36.8/s |
| lock 처리량 | 73.5/s | 46.1/s |
| 요청당 CPU | 9.6~10.2ms | 13.6~22.1ms |
| 스로틀 | 12~18% | 최대 51% |

**Pod를 늘렸는데 처리량이 절반이 됐다.** 두 가지가 겹쳤다.

1. **예열이 Pod 수만큼 쪼개졌다.** 버리는 부하 300건이 두 JVM에 150건씩 나뉘어
   각자 절반만 데워졌다. 요청당 CPU가 9.6 → 17ms로 오르면 같은 CPU로 처리할 수 있는
   요청이 104건 → 59건으로 준다. **JIT 컴파일러 자신이 컨테이너 쿼터를 먹는다**는 점도
   겹쳐(스로틀 51%), 덜 데워진 JVM은 이중으로 손해를 본다.
2. **병목이 backend가 아니다.** 같은 실행에서 Hikari는 한가했고(pending 0~10)
   요청은 게이트웨이 단계에서 잘렸다. **뒤를 두 배로 넓혀도 앞의 깔때기는 그대로다.**

> 예열 교란이 섞여 있어 "**효과 없음**"까지만 말할 수 있고 "더 나쁘다"는 못 박는다.
> 다만 **사전 확보로 나아진다는 근거는 없다.**

### 5-3. 게이트웨이 503 — 원인 추적

`AUTHENTICATION_SERVICE_UNAVAILABLE`(503)이 실행마다 0~13%로 나타났다.
게이트웨이는 모든 요청에서 JWT 블랙리스트를 Redis로 확인하고, 정해진 시간을 넘기면
fail-closed로 503을 낸다(`JwtAuthenticationGlobalFilter`).

**Redis는 무죄다.** 부하 직후 `commandstats`:

```
exists     1,207회   2.27 µs/call    <- 블랙리스트 조회
evalsha      569회  80.46 µs/call    <- 재고 차감 Lua
Redis 가 실행 내내 쓴 서버 시간 합계 = 48ms
```

타임아웃은 이미 2000ms였다. **2.27µs짜리 작업이 2초를 넘겼다면 Redis가 늦은 게 아니라
게이트웨이가 응답을 처리할 CPU를 못 잡은 것이다.** 그리고 k6를 다른 호스트로 옮기자
**503이 31건 → 2건 → 0건으로 사라졌다.** 원인은 게이트웨이의 절대적 자원 부족이 아니라
**부하 생성기와의 코어 경합**이었다.

> **`request`와 `limit`을 구분해야 한다.** 경합 시 CPU 몫은 cgroup v2의 `cpu.weight`가
> 정하고, 그 값은 **request**에서 나온다. limit 상향은 노드가 한가할 때만 의미가 있고,
> 정확히 문제가 되는 버스트 구간에서는 아무것도 바꾸지 않는다.
> 실제로 게이트웨이 limit을 500m → 1000m으로 올려봤으나 효과가 없어 되돌렸다.

## 6. 결과 — 지연 예산 (1차, 맥에서 부하)

게이트웨이의 서버측(`http_server_requests`)과 클라이언트측(`http_client_requests`)
누적 지표를 빼면 구간이 갈린다. lock 평균 4.47초 기준.

| 구간 | 시간 | 비중 |
| --- | ---: | ---: |
| backend 서블릿 | 0.34s | 8% |
| Tomcat 큐 + 파드 간 네트워크 | 0.49s | 11% |
| 게이트웨이 필터 체인 (JWT 검증·블랙리스트·라우팅) | 0.43s | 10% |
| **부하 생성기 → 인터넷 → Traefik → 게이트웨이** | **~3.2s** | **71%** |

같은 실행에서 backend는 **Tomcat 스레드 200개 중 4개**만 바빴다. 완전히 유휴다.

**서버 안쪽만 합치면 약 1.3초로 NFR(1.5초) 근처다.**
지금 보이는 p95는 애플리케이션이 아니라 측정 경로를 재고 있다.

## 7. 지연은 어디서 생기는가 — 경로 분해

§6 에서 지연의 대부분이 backend 밖에 있다는 것까지 확인했다. 그 "밖"을 갈랐다.

### 방법

**같은 JVM·같은 예열 상태에서 경로만 바꿔 세 번 잰다.** `TodayDropCache` 가 당일
드롭을 리스트로 들고 기동 시 refresh 하므로, 롤아웃 **전에** 드롭 4개를 만들어두면
한 번의 기동으로 전부 캐시에 올라온다. 1번으로 데우고 2·3·4번을 각 경로에 쓴다.
경로마다 롤아웃하면 예열 상태가 달라져 경로 차이인지 예열 차이인지 구분할 수 없다.

```bash
PREP_ONLY=true DROP_COUNT=4 ./warm-measure.sh paths 300 300
```

부하 생성기는 node-b 의 Pod 로 띄운다. 측정 대상(backend·게이트웨이·Traefik)은
전부 node-a 에 고정한다(`nodeSelector` + HPA `min=max=1`). 그래야 부하 생성기가
측정 대상의 코어를 뺏지 않는다 — 이 격리를 빼먹으면 backend 가 k6 와 같은 노드로
가서 처리량이 절반이 된다(실측).

| 경로 | 대상 | 빼는 것 |
| --- | --- | --- |
| A | `https://<공인IP>.sslip.io` | — (기준선) |
| B | 같은 URL, `hostAliases` 로 Traefik ClusterIP 에 직결 | 공인 IP 헤어핀(NAT/IGW) |
| C | `http://api-gateway:8080` | Traefik + TLS |

B 에서 `hostAliases` 를 쓰는 이유는 **Host 헤더를 유지**하기 위해서다. Traefik 이
Host 로 라우팅하므로 IP 로 직접 치면 룰에 걸리지 않는다. C 는 `default-deny-ingress`
때문에 임시 NetworkPolicy 가 필요하다(측정 후 삭제).

### 결과 (lock, 300 동시, 실패 0)

| 경로 | 클라이언트 평균 | p95 | 처리량 |
| --- | ---: | ---: | ---: |
| A 공인 IP | 3.05s | 5.29s | 29.0/s |
| B Traefik 직결 | 2.96s | 5.24s | — |
| **C 게이트웨이 직접** | **1.68s** | **2.54s** | **53.6/s** |

```
A - B = 0.09s   공인 IP 헤어핀 몫       작다
B - C = 1.28s   Traefik + TLS 몫        여기가 최대
```

서버 측 누적 카운터(같은 구간):

```
구간        요청    backend 서블릿   gw 총처리   gw 업스트림   gw 필터체인
A lock      315         138ms         947ms       313ms        634ms
B lock      314         130ms         710ms       298ms        412ms
C lock      307         130ms         782ms       252ms        529ms
```

**backend 서블릿은 세 경로 모두 130~138ms 로 같다.** 경로를 바꿔도 backend 가
하는 일은 변하지 않는다.

### 지연 예산 (경로 A, 평균 3.05초)

| 구간 | 시간 | 비중 |
| --- | ---: | ---: |
| **Traefik + TLS 핸드셰이크** | **~1.28s** | **42%** |
| 게이트웨이 필터 체인 (JWT 검증 + 블랙리스트) | 0.63s | 21% |
| 클라이언트 연결 수립·큐 (경로 C 에도 남는 몫) | ~0.90s | 29% |
| 게이트웨이 → backend 큐·네트워크 | 0.18s | 6% |
| **backend 서블릿** | **0.14s** | **5%** |
| 공인 IP 헤어핀 | 0.09s | 3% |

### TLS 핸드셰이크가 최대 비용인 이유

핸드셰이크 하나가 50~70ms 다(실측). 드롭 오픈은 **300명이 동시에 새 연결을 맺는다.**

```
300건 x 60ms = 18 CPU-초
Traefik CPU limit = 1000m
```

**1코어로 18초어치 암호 연산을 몇 초 안에 끝내야 하니 줄이 선다.**
평상시에는 드러나지 않고 버스트에서만 나타나는 성질의 병목이다.

게이트웨이 필터 체인 0.63초도 작지 않다 — 요청마다 JWT 서명 검증과 Redis
블랙리스트 왕복이 붙는다.

## 8. 개선 — 무엇을 바꿨고 얼마나 나아졌나

§7에서 지연의 대부분이 진입점에 있다는 것까지 갔다. 두 가지를 바꿔 확인했다.

### 8-1. TLS 인증서를 RSA-4096에서 ECDSA P-256으로

`openssl s_client` 로 확인해보니 인증서가 **RSA 4096비트**였다. Traefik ACME의
기본값(`keyType: RSA4096`)이라 의도해서 고른 값이 아니었다.

TLS 1.3에서 핸드셰이크마다 **서버가 개인키 서명을 한 번** 한다. 그 연산 비용을
측정 노드에서 직접 쟀다(`openssl speed`).

| | 서버(서명) | 클라이언트(검증) |
| --- | ---: | ---: |
| **RSA 4096** | **186.8회/s** | 10,843회/s |
| RSA 2048 | 1,140.9회/s | — |
| **ECDSA P-256** | **28,201회/s** | 8,778회/s |

```
300건 핸드셰이크에 필요한 CPU
  RSA 4096     1.61초    <- Traefik limit 은 1코어다
  ECDSA P-256  0.011초
```

§7에서 잰 "Traefik + TLS 몫 1.28초"가 이 한 연산으로 거의 설명된다.

**클라이언트 검증은 19% 느려지지만** 요청당 1회뿐이라 체감되지 않는다.
보안 강도는 P-256이 RSA 3072 상당으로 4096보다 낮으나 현실적 공격 임계보다
한참 위이고, 주요 CDN의 기본 선택이다.

적용은 `k8s/cluster/traefik/helm-chart-config.yaml` 에 한 줄이다.

```
--certificatesresolvers.letsencrypt.acme.keytype=EC256
```

> **주의**: `keytype`만 바꾸면 `acme.json`에 저장된 기존 인증서를 만료 30일 전까지
> 계속 쓴다. 전환하려면 저장된 인증서를 지워 재발급을 유도해야 하고, 그 사이
> 짧게 자체 서명 인증서로 응답한다. 실측에서는 재발급이 5초 안에 끝났다.

### 8-2. 게이트웨이 CPU request 100m → 300m

ECDSA 전환 후 **재사용 경로가 오히려 나빠졌다**(p95 3.26s → 4.25s). 핸드셰이크가
만들던 자연스러운 도착 분산이 사라지면서 300건이 같은 순간에 게이트웨이를 치기
때문이다. 이때 게이트웨이의 상태를 PSI로 봤다.

```
게이트웨이 CPU 사용   0.15코어   (limit 500m)
스로틀              0회
cpu.pressure        some 63%  full 57%
```

**`full 57%`** — 전체 시간의 절반 이상 동안 게이트웨이의 **모든 스레드가 동시에
멈춰** 있었다. 쿼터의 1/3만 쓰면서. `cpu.stat`의 `throttled_usec`은 0이라
스로틀 지표만 보면 정상으로 보이는 구간이다. **자기 쿼터가 아니라 노드 스케줄러가
CPU를 안 준 것**이고, 그 배분을 정하는 것이 `request`다(cgroup v2 `cpu.weight`).

node-a는 CPU request가 100%(2000m/2000m)라 자리를 만들어야 했다.

| Pod | request | 유휴 실사용 | 조치 |
| --- | ---: | ---: | --- |
| elasticsearch | 300m | 8m | **150m** (검색 여유는 남김) |
| ai-service | 250m | 7m | **100m** (드롭 경로 무관) |
| kafka | 200m | 197m | 그대로 (실제로 씀) |
| **api-gateway** | **100m** | 11m | **300m** |
| backend | 500m | 부하 시 550~800m | **그대로** |

**backend는 줄이면 안 된다.** "병목이 아니다"는 "빨리 끝낸다"는 뜻이지
"CPU를 안 쓴다"는 뜻이 아니다. 부하 구간 실측이 0.55~0.8코어이고, request는
HPA 목표(65%)의 기준이기도 하다.

### 8-3. 결과

lock, 300 동시, 모두 실패 0.

| | ① RSA-4096 / gw 100m | ② ECDSA / gw 100m | **③ ECDSA / gw 300m** |
| --- | ---: | ---: | ---: |
| **신규연결 p95** | 5.82s | 2.58s | **2.41s** |
| 신규연결 처리량 | 36.8/s | 103.3/s | **101.2/s** |
| **재사용 p95** | 3.26s | 4.25s | **0.886s** |
| 재사용 평균 | 1.80s | 2.94s | **0.420s** |

**연결 재사용 경로가 NFR(p95 1500ms)을 통과했다.** ①→③ 대비 3.7배다.

서버 측 구간이 그 이유를 보여준다.

```
                     gw 100m        gw 300m
게이트웨이 총처리     1,929ms   →     355ms
  + 업스트림          1,232ms   →     180ms
  + 필터 체인           697ms   →     174ms
게이트웨이 CPU         0.15코어  →    0.25코어
PSI full                57%     →      35%
backend 서블릿         497ms    →     221ms
```

**CPU 사용량이 늘면서 시간이 줄었다** — 같은 일을 하는데 CPU를 더 받아 더 빨리
끝냈다는 뜻이다. 쿼터(500m)에는 여전히 안 닿는다. `request`가 정확한 지렛대였다.
게이트웨이가 요청을 덜 몰아치니 backend 쪽 큐도 얕아졌다(497 → 221ms).

### 8-4. 두 조치는 서로 다른 구간을 고친다

| 조치 | 고치는 것 | 효과 |
| --- | --- | --- |
| ECDSA 인증서 | **신규 연결** 경로의 핸드셰이크 | p95 −56%, 처리량 2.8배 |
| 게이트웨이 request | **순간 동시성**을 받아내는 능력 | p95 −79% |

**하나만 해서는 안 됐다.** ECDSA만 적용했을 때 재사용 경로는 오히려 나빠졌다.

### 8-5. 남은 것

**신규 연결 경로는 p95 2.41초로 아직 NFR을 넘는다.** 다만 이 경로는 "드롭 시간에
맞춰 새로 접속하는 사용자"이고, 브라우저가 h2로 연결을 재사용하는 다수 경로는
통과한다. ALPN은 이미 `h2`로 협상되고 있다.

## 9. 배포와 배치 — 운영에서 확인된 것

성능 측정과 별개로, 이 클러스터의 배포 동작에서 확인된 것들이다. 절대 수치보다
오래 가는 내용이라 함께 남긴다.

### 9-1. 동시 롤아웃은 2코어 노드에서 실패한다

`deploy.yml` 이 `kubectl apply -k` 한 번으로 5개 Deployment 를 동시에 롤링하고
`rollout status` 만 순차로 기다리고 있었다. 실제 동시성은 5다.

2026-08-26 배포에서 새 Pod 4개가 한 노드에 몰려 **전부 startupProbe 를 넘기지 못하고
7~8회씩 재시작**했다. 옛 Pod 가 살아 있어 서비스는 유지됐지만 10분 가까이 서로를 죽였다.

```
node-a  CPU 1999m / 2000m (99%)   PSI some 98%   load 12.3
node-b  CPU  199m / 2000m  (9%)
```

**스케줄링과 기동은 다른 문제다.**

| | 판단 근거 | 그날 결과 |
| --- | --- | --- |
| 스케줄링 | `request` 합계만 봄 | **성공** — 장부상 자리가 있었다 |
| 기동 | 노드의 **실제 CPU** | **실패** — 실사용이 이미 포화 |

예약과 실사용의 괴리가 원인이다. elasticsearch 는 300m 예약에 실사용 9m, kafka 는
200m 예약에 실사용 266m 이었다. 스케줄러는 이 차이를 모른다.

**해결**: 전부 `rollout pause` 한 뒤 apply 하고 하나씩 `resume` 한다. 중간 실패로
일시정지가 남으면 이후 배포가 조용히 무시되므로 `trap` 으로 재개를 보장한다.
적용 후 첫 배포에서 **재시작 0회**로 완료됐다(직전 배포는 실패).

### 9-2. `maxSurge` 는 선호 노드에 자기 몫의 두 배를 요구한다

`maxSurge: 1` 이면 옛 Pod 가 자원을 쥔 채로 새 Pod 가 떠야 한다. 선호 노드에
**자기 request 만큼 추가 여유**가 없으면 반대 노드로 밀리고, 거기 눌러앉는다
(`IgnoredDuringExecution` 이라 자리가 나도 돌아오지 않는다).

노드가 90% 넘게 예약된 상태에서는 배포마다 서비스가 노드를 오간다. 실제로
member/payment 는 자기 DB(node-b)와 갈려 node-a 에, backend 는 core-postgres(node-a)와
갈려 node-b 에 있었다 — **설계 문서의 배치 원칙이 통째로 뒤집혀 있었다.**

`preferred` nodeAffinity 는 이걸 막지 못한다. 자원 필터를 통과한 노드들 사이의
점수일 뿐이라, 자리가 없으면 점수를 매길 기회조차 없다.

### 9-3. backend 는 배포마다 노드가 바뀐다 (알려진 동작)

```
podAntiAffinity: required (hostname) + maxSurge: 0 + replica 1
```

새 Pod 가 스케줄될 때 **종료 중인 옛 Pod 가 아직 그 노드를 점유**한다. 그래서
anti-affinity 와 자원 양쪽에서 그 노드가 제외되고, 반드시 반대 노드로 간다.
`FailedScheduling` 없이 즉시 반대편에 배치되므로 로그만 봐서는 드러나지 않는다.

**롤아웃 순서를 바꿔도 해결되지 않는다** — 원인이 자기 자신이다.

| 대응 | flip | 배포 중단 | 상시 자원 |
| --- | --- | --- | ---: |
| **그대로 둔다 (현재)** | 매 배포 | 90초 | 500m |
| HPA `minReplicas: 2` | 없음 | 없음 | 1000m |
| `nodeSelector: core` | 없음 | 90초 | 500m — **단 replica 2가 영원히 Pending** |

`nodeSelector` + `required podAntiAffinity` 조합은 **replica 를 최대 1개로 묶는다.**
HPA `max: 2` 가 무력화되므로 쓰면 안 된다.

**현재는 그대로 둔다.** node-b 에 있을 때의 비용은 요청당 약 4ms(실측 노드 간 왕복
0.69ms × 5~6회)로 지연의 0.5% 다. 되돌리려면 90초 중단을 감수해야 하고 다음 배포에
또 뒤집히므로 수지가 맞지 않는다. `minReplicas: 2` 로 가면 자연히 사라진다.

### 9-4. 목표 배치와 그 근거

| | node-a (core, 8GB) | node-b (service, 4GB) |
| --- | --- | --- |
| 앱 | traefik · api-gateway · backend | member-service · payment-service · ai-service |
| 데이터 | core-postgres · redis · kafka · elasticsearch · ai-postgres | member-postgres · payment-postgres |
| 관측 | — | prometheus · grafana · 익스포터 |
| CPU 예약 | 1800m (90%) | 1045m (52%) |

**stateful 5개는 `local-path` PV 라 node-a 에 못 박혀 있다.** 여기에 드롭 경로(traefik ·
gateway · backend)와 시스템 Pod 를 더하면 그것만으로 1800m 이다. member/payment/ai
셋은 애초에 node-a 에 들어갈 자리가 없고, 그중 둘은 자기 DB 가 node-b 에 있어
오히려 맞는 배치다.

ai-service 만 DB(ai-postgres)와 갈리는데, 이 서비스의 지연은 OpenAI 임베딩
호출(200~500ms)이 지배하므로 노드 간 왕복 5ms 는 1~2% 다.

## 10. 확인된 병목

| 순위 | 병목 | 근거 | 성격 |
| ---: | --- | --- | --- |
| ~~1~~ | ~~**Traefik 의 TLS 핸드셰이크**~~ | 인증서가 RSA-4096이라 서명이 초당 186회였다 | **해결(§8-1).** ECDSA P-256 전환 |
| ~~2~~ | ~~**게이트웨이 필터 체인**~~ | 일이 아니라 대기였다. PSI full 57% | **해결(§8-2).** request 100m→300m |
| 3 | **`@Transactional` 안의 Redis 왕복** | 커넥션 점유가 유휴 17ms → 부하 135ms (8배) | **설계.** 환경 무관 |
| 4 | JIT 예열 | 예열 유무로 p95가 2배 | 측정 방법론 |
| 5 | 부하 생성기의 위치 | 측정 대상과 같은 노드면 처리량 절반, 503 최대 13% | 측정 환경 |
| — | ~~Hikari 풀 10~~ | 풀 20으로 올려도 p95가 0.5%만 변함 | **기각** (§8) |
| — | ~~backend CPU~~ | 지연의 5%. Tomcat 200개 중 4~61개만 사용 | **기각** (§7) |

### 1순위가 왜 중요한가

`DropLockService`가 `@Transactional` 안에서 Redis 응답을 기다리는 동안 DB 커넥션을
쥐고 있다. UPDATE 1건 + Redis Lua 1회짜리 작업에 점유 135ms는 과하다.

```
풀 10 ÷ 점유 135ms = 이론 74 req/s
풀 10 ÷ 점유  20ms = 이론 500 req/s
```

**DB 부하를 늘리지 않고 처리량을 올리는 유일한 방법이다.**

다만 현재 순서에는 명시된 설계 의도가 있다.

> Redis가 실패하면 예외를 던져 트랜잭션이 롤백되면서 `drop_entry`도 원래 상태로
> 되돌아가므로 별도의 보상 로직이 필요 없다. 순서를 뒤집으면 Redis를 되돌리는 보상
> 호출이 필요해지고, 그 보상마저 실패하면 재고가 영구히 누락된다.

**정합성과 처리량의 교환이므로 팀 논의가 필요하다.**

### Hikari 풀을 기각한 근거

풀 10에서 커넥션 대기(acquire)가 496ms, pending이 48까지 갔다. 풀 20으로 올리자
대기는 156ms로 3분의 1이 됐다. **그런데 p95는 3.65s → 3.63s로 움직이지 않았다.**

**커넥션 대기는 응답시간의 지배 항목이 아니었다.** 풀 상향은 큐를 Hikari 앞에서
CPU 앞으로 옮겼을 뿐이다. (해롭지도 않아 20은 그대로 유지한다.)

| 7 | 신규 연결 경로 p95 2.41초를 더 줄일지 판단한다 | 아직 NFR 초과. 다만 브라우저는 h2로 연결을 재사용한다 (§8-5) |
| 8 | 게이트웨이 블랙리스트에 짧은 로컬 캐시를 검토한다 | 요청마다 Redis 왕복 1회. **정합성과의 교환** |
| 9 | 트랜잭션 범위 축소를 설계 과제로 올린다 | 코드 안에서는 가장 큰 지렛대 (§9) |
| 10 | 부하 생성기는 측정 대상과 다른 노드에 둔다 | 같은 노드면 처리량 절반, 503 최대 13% (§7) |
| 11 | elasticsearch request를 더 줄일지는 검색 부하를 섞어 재본 뒤 정한다 | 유휴 실사용(8m)만 확인했다 |
| 12 | **api-gateway·backend `replicas: 2`** 를 검토한다 | 배포 중단(backend 90초)과 노드 flip 을 함께 없앤다. 상시 자원 +800m (§9-3) |
| 13 | 서비스별 JVM 힙(`-Xmx`)을 명시한다 | node-b 에 JVM 3개가 모여 메모리 limit 합이 용량의 102% 다. backend 만 명시돼 있다 |

8번과 9번은 **정합성과 처리량의 교환**이다. 블랙리스트 캐시는 로그아웃한 토큰이
TTL 만큼 계속 통하고, 트랜잭션 범위 축소는 Redis 보상 로직이 필요해진다.
둘 다 팀 논의가 필요한 사안이다.

## 12. 재현 방법

```bash
# 서버(EC2)에서. 드롭 생성이 kubectl exec로 DB를 직접 친다
export KUBECONFIG=$HOME/.kube/config
cd performance-test/loadtest

# 게이트웨이로 직접 (Traefik·인터넷 제외)
kubectl -n openbake port-forward svc/api-gateway 18080:8080 &
CORE_BASE_URL=http://127.0.0.1:18080 ./warm-measure.sh <라벨> 300 300

# 구간 지표
python3 poll-report.py ../results/loadtest/warm-<라벨>/poll.csv
```

구간이 5개 나온다. **뒤의 두 개(측정 confirm/lock)에서 요청당 CPU가 평평한지**
먼저 확인한다. 계속 내려가고 있으면 예열이 부족한 것이라 그 숫자로 비교하면 안 된다.

```
1번  조회 예열 300회
2번  버리는 confirm      <- 여기 pending 170, 스로틀 44%가 "예열 안 된 상태"의 민낯
3번  버리는 lock
4번  측정 confirm        <- 여기부터가 값
5번  측정 lock
```

### 함정

| 함정 | 증상 | 대응 |
| --- | --- | --- |
| 토큰 30분 만료 | 전부 401 | 하네스가 15분 미만이면 자동 재발급 |
| 예열 누락 | 요청당 CPU 2배, p95 2배 | 쓰기 경로까지 예열 (§3) |
| 예열 대기 단축 | 30초로 줄이면 p95가 3.5s → 8.0s | 60초 미만으로 내리지 않는다 |
| 스크립트 동시 실행 | 로그·결과가 뒤섞이고 폴러가 죽는다 | `flock`으로 차단됨 |
| `port-forward` 사망 | 전부 `000` | 측정 전 `curl`로 확인 |
| 계정 생성 동시성 과다 | 로그인 실패 | `ACCOUNT_WORKERS=8` |
| replica 2에서 폴러 공백 | cgroup을 못 읽음 | 로컬 노드 Pod를 고르도록 수정됨 |

## 13. 한계

- **표본 300, 1회 실행.** p95는 285번째 값 하나이고 **p99는 뒤에서 3번째 값이라 못 쓴다.**
  같은 구성 재현 오차가 약 6%이므로 **20% 미만 차이는 구분할 수 없다.**
- 부하가 6초에 끝나는 **버스트**다. 정상상태 처리량이 아니라 배수 시간을 잰다.
  도메인(드롭 오픈)과는 맞지만, 일반적인 용량 산정에는 쓸 수 없다.
- 측정 경로가 두 가지였고 **둘 다 왜곡이 있다.**
  서버에서 k6를 돌리면 코어를 뺏고, 다른 호스트에서 돌리면 인터넷 왕복이 지연을 지배한다.
- `replica 2` 측정은 예열이 Pod 수만큼 쪼개진 상태였다. 공정한 비교를 하려면
  예열 부하를 Pod 수에 비례해 늘려야 한다.
